Entra concepts

The background needed to read the rest of the documentation. Skip it if you know Entra.

Tenant

A tenant is one directory. It holds users, groups and applications, and has a GUID and at least one domain name. The simulator serves the tenant 00000000-0000-0000-0000-000000000001 with the domain entra-sim.test by default, and can serve more tenants. A path can name a tenant by GUID or by domain. Entra also accepts the aliases common, organizations and consumers, and the simulator accepts all three.

Users and groups

A user's main name is its userPrincipalName, for example alice@entra-sim.test, compared without case. A group holds users, other groups and service principals. Members are not part of the group object; they are read and changed through separate paths:

GET    /v1.0/groups/{id}                    the group, with no members
GET    /v1.0/groups/{id}/members            direct members
GET    /v1.0/groups/{id}/transitiveMembers  members of nested groups as well
POST   /v1.0/groups/{id}/members/$ref       {"@odata.id": "https://graph.microsoft.com/v1.0/directoryObjects/{member-id}"}

The URL in @odata.id names the real Graph host. Only the last path segment is read.

Application and service principal

An app in Entra is two objects:

ObjectWhat it is
Application (app registration)The definition: secrets, certificates, redirect URIs, the permissions it requests, the app roles and scopes it defines as an API.
Service principal (enterprise app)The identity in one tenant. Assignments point at it, and app-only tokens represent it.

An application has an object ID (id), used in Graph paths, and a client ID (appId), used at the token endpoint. Entra generates both. Microsoft Graph is itself an application with the appId 00000003-0000-0000-c000-000000000000; a tenant holds only its service principal.

App roles and delegated scopes

TypeToken claimHeld byGranted by
App rolerolesAn application acting as itself, or a user, or a group's membersAn appRoleAssignment: principalId, resourceId (the API's service principal), appRoleId
Delegated scopescpAn application acting for a signed-in userConsent, recorded as an oauth2PermissionGrant

Every API defines its own roles and scopes, and a role or scope means something only in a token for the API that defines it. A permission can exist in both forms with different GUIDs. For Graph, Application.ReadWrite.All is the app role 1bfefb4e-e0b5-418b-a88f-73c46d2cc8e9 and the delegated scope bdfbf15f-ee85-4955-8675-146e8e5296b5. Terraform configurations name them by these GUIDs, which is why the simulator carries Microsoft's catalogue (see generated data).

Directory roles

A directory role, such as Global Administrator, gives administrative rights over the directory. Entra has built-in role templates; a template is activated into a directoryRole object, which then has members. /roleManagement/directory is a newer view over the same roles. Privileged Identity Management (PIM) makes a user eligible for a role, to activate for a limited time. An administrative unit narrows a role to the users and groups in that unit.

Tokens

Entra issues RS256-signed JSON Web Tokens. A client validates one by reading kid from the header, fetching the OIDC discovery document, following its jwks_uri, finding the key with that kid, and checking the signature, aud, iss and exp. An app-only token carries roles; a user token carries scp, and roles when the user holds app roles on the API. Tokens lists every claim the simulator issues.

The main flows

Client credentials

A service gets a token for itself. scope is {api}/.default, which means "every app role I hold on that API".

POST /{tenant}/oauth2/v2.0/token
grant_type=client_credentials&client_id=…&client_secret=…&scope=https://graph.microsoft.com/.default

Authorization code with PKCE

The client sends the browser to /{tenant}/oauth2/v2.0/authorize with a code_challenge (the SHA-256 of a random verifier). The user signs in and consents, and the browser returns to the redirect_uri with a code. The client exchanges the code and the code_verifier for an access token, an ID token and, with offline_access, a refresh token. A stolen code is useless without the verifier.

Refresh token

The client exchanges a refresh token for a new access token. Entra rotates refresh tokens: the response has a new one and the client stores it.

The simulator also implements the on-behalf-of, device code and password grants, described in Identity endpoints.
