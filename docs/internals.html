Internals

The source layout, the data generated from Microsoft's documentation, the design decisions behind them, and how the simulator is verified.

Generated data

Three files are generated from Microsoft's published documentation by scripts/generate-*.py, not written by hand, because configurations name the real identifiers and an invented one would break them.

The route list the requirement generator covers is in the script; a route added to the simulator is added there too. CI regenerates all three on every push and pull request and fails when one differs.

Design decisions

  • TLS in the simulator. The provider forces https when it fetches the metadata document, so a plain HTTP simulator cannot serve Terraform.
  • Unknown properties are kept. Each entity keeps properties it does not model in an extra map and returns them, including explicit nulls, so terraform plan after apply is empty.
  • Claims are read from the directory at issuance. Roles, scopes, groups and directory roles are never cached in a session, so deleting an assignment or grant changes the next token, as revocation should.
  • The check runs in the extractor. Permission enforcement runs inside the Caller extractor every Graph handler takes, so no route can skip it.
  • Unmapped routes are allowed. A route missing from the generated table is a gap in the simulator; refusing would break a client the real service serves. The warning in the log surfaces it.
  • Stable order. Collections are BTreeMaps keyed by object ID, which keeps $skiptoken paging stable.
  • A bad seed stops startup. An empty tenant would look like a working simulator with lost data.
  • Stable bootstrap IDs. The bootstrap objects' IDs derive from the client ID, so Terraform state written against them survives a restart.

Verification

CI jobWhat it checks
Format, lint and testcargo fmt --check, cargo clippy --all-targets -- -D warnings, cargo test
Generated files are up to dateRegenerates the three data files from Microsoft's documentation and fails if one differs
Build the simulatorCompiles the release binary once for the provider contract, Terraform and browser jobs
Container imageBuilds the image and checks that it serves requests
Provider contractRuns contract/envcheck, the provider's go-azure-sdk discovery and token code at the version the provider pins, against the simulator
Terraform acceptanceApplies tests/terraform/, requires terraform plan -detailed-exitcode to exit 0, then destroys
Browser clientRuns the React example's Playwright suite in Chromium

The release workflow runs on a version tag: it repeats format, lint and test, checks that the tag matches the crate version, publishes the image to ghcr.io/gosogco/entra-sim, checks the published image, and creates the GitHub release.
