How a scope names an API

A token is for one API. The scope parameter names it, as in Entra:

  • {resource}/{value} or {resource}/.default, where {resource} is one of the API application's identifierUris or its appId. .default asks for every permission already granted.
  • A bare value such as User.Read names Microsoft Graph.
  • https://graph.microsoft.com and the simulator's own base URL (https://localhost:8443 by default) both name Graph. Nothing is sent to Microsoft; the name is only matched.
  • openid, profile, email and offline_access govern what is issued, not which API.

The API must have a service principal in the tenant. An unknown API gives 400 invalid_resource with AADSTS500011. Scopes for two APIs in one token request give AADSTS700022. A sign-in may name scopes on several APIs: consent is recorded for each, and the code is redeemed for the API in the token request's own scope, or the first API the sign-in named. A sign-in that names no API yields a Graph token. A scope value the API does not publish is never consented and never reaches scp.

Grants

Client credentials

POST /{tenant}/oauth2/v2.0/token
grant_type=client_credentials
client_id=…
client_secret=…           (or client_assertion and client_assertion_type)
scope={resource}/.default

The client must authenticate. The token's roles are the values of the app roles assigned to the client's service principal on that API, read from the directory at issuance, so deleting an assignment changes the next token. The scope must end in /.default; anything else gives AADSTS70011.

Authorization code, with or without PKCE

GET /{tenant}/oauth2/v2.0/authorize?client_id=…&response_type=code
    &redirect_uri=…&scope=openid offline_access User.Read&state=…
    &code_challenge=…&code_challenge_method=S256
    [&response_mode=query|fragment|form_post] [&prompt=…] [&login_hint=…] [&nonce=…]

The authorize request is checked before any page is shown. These failures are displayed rather than redirected, because the redirect target is not trusted yet:

  • The client is unknown (AADSTS700016) or has no service principal (AADSTS650052).
  • The redirect_uri is not among the application's web, spa or publicClient redirect URIs (AADSTS50011).
  • response_type is not code (AADSTS70005). The implicit and hybrid flows are not implemented.
  • code_challenge_method is neither S256 nor plain.

After sign-in the code is returned according to response_mode: in the query string, in the URL fragment (which msal-browser uses), or as an HTML page that posts a form with code and state to the redirect URI. A code lives 10 minutes and is redeemed once:

The response holds access_token, id_token when openid was asked for, and refresh_token when offline_access was asked for.

Refresh token

POST /{tenant}/oauth2/v2.0/token
grant_type=refresh_token&client_id=…&refresh_token=…[&scope=…]

Refresh tokens live 90 days and are rotated: each use returns a new one and the old one stops working (AADSTS700082). A refresh token works for any API the user consented to for that client. One issued to another client gives AADSTS70000. A conditional access policy that needs MFA the original sign-in did not do gives interaction_required.

On-behalf-of

POST /{tenant}/oauth2/v2.0/token
grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer
requested_token_use=on_behalf_of
assertion={a user token for the middle-tier API}
client_id=…&client_secret=…
scope={downstream API scopes}

A middle-tier API exchanges a user's token for a token for another API. The rules follow Microsoft's on-behalf-of documentation:

  • The client must authenticate.
  • The assertion must be a token this simulator issued, v1.0 or v2.0, whose aud is the calling application, and it must be a user token. Otherwise AADSTS50013.
  • scp comes from consent the user gave the middle tier for the downstream API. Without it, invalid_grant with AADSTS65001.
  • roles are the user's own roles on the downstream API, never the middle tier's.
  • MFA carries over when the assertion's amr includes mfa.
  • A refresh token is returned when offline_access is requested.

Password (resource owner password credentials)

POST /{tenant}/oauth2/v2.0/token
grant_type=password&client_id=…&username=…&password=…&scope=…
  • Refused on common and consumers (AADSTS90023); organizations and a tenant are accepted.
  • The application is a public client when its isFallbackPublicClient is true. A public client must not send a secret or assertion (AADSTS700025); a confidential client must (AADSTS7000218).
  • The password is the one set in the user's passwordProfile. A wrong password, or a user without one, gives AADSTS50126. A disabled user gives AADSTS50057.
  • Scopes not yet consented give consent_required (AADSTS65001). There is no page to consent on.
  • A conditional access policy that needs MFA gives interaction_required (AADSTS50076).

UserInfo

/oidc/userinfo takes a Graph access token whose scp includes openid. It returns sub; name, given_name, family_name and picture when profile was granted; and email when email was granted and the user has a mail address. A token for another API, or an app-only token, is refused.

Client authentication

A confidential client authenticates with one of:

CredentialHow it is checkedappidacr / azpacr
Client secret, in the body or with HTTP BasicAgainst the application's passwordCredentials, including their start and end dates. Wrong: AADSTS7000215.1
Certificate assertionA JWT signed with the private key of a certificate in the application's keyCredentials, found by the x5t#S256 header or the older x5t. PS256 and RS256 are accepted. aud is the token endpoint URL, iss and sub are the client ID, and jti, nbf and exp are required. A bad signature gives AADSTS700027; bad claims give AADSTS50027.2
Federated identity credentialA JWT from an external issuer, such as a GitHub Actions token. Its iss, sub and aud must match one of the application's federated identity credentials exactly (AADSTS70021 otherwise). The simulator then fetches the issuer's /.well-known/openid-configuration and keys over HTTPS and checks the signature. A token issued by the simulator itself is refused (AADSTS700229).2

Assertions are sent as client_assertion with client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer, on every grant that takes a secret. A public client sends nothing and gets 0.

Federated credentials are the only feature that makes outbound network requests.

The sign-in page and sessions

The sign-in page lists the tenant's users and the permissions the client requests. It is self-contained and works without network access. Choosing a user records consent as an oauth2PermissionGrant, so scp comes from the directory: a client cannot widen its own token, an operator sees the consent with GET /v1.0/oauth2PermissionGrants, and deleting the grant narrows the next token. {resource}/.default applies static consent: every permission on the client's registration (requiredResourceAccess), including APIs that list the client in api.knownClientApplications. A client listed in an API's api.preAuthorizedApplications needs no consent for the listed scopes.

Signing in sets the cookie entra_sim_session for 24 hours. With it:

ParameterBehaviour
noneA browser with a session and the needed consent signs in without a page.
prompt=noneSigns in silently. Without a session it redirects with login_required (AADSTS50058); when consent is missing, with interaction_required (AADSTS65001).
prompt=loginShows the user picker even with a session.
prompt=select_accountShows the user picker even with a session.
prompt=consentShows the consent step even when consent exists.
login_hintLists the user with that user principal name first. A session for a different user is not reused.

/{tenant}/oauth2/v2.0/logout clears the session. --auto-sign-in-user {upn} signs that user in without a page for tests that cannot drive a browser; prompt=login still forces the page.

Assignment required

When an API's service principal has appRoleAssignmentRequired set to true:

  • A user gets a token for it only when the user, or a security group the user is a direct member of, holds an app role assignment on it. The default access role (the all-zero GUID) counts. Global Administrators are exempt. Otherwise AADSTS50105.
  • A client credentials token needs an assignment of the client on it. Otherwise AADSTS501051.

More than one tenant

--additional-tenant TENANT_ID=DOMAIN (ENTRA_SIM_ADDITIONAL_TENANTS, comma-separated) serves more tenants beside the primary one. Each has its own directory with Microsoft Graph and the bootstrap client.

  • The identity endpoints take the tenant from the path. Graph takes it from the token's tid.
  • Through common or organizations, the sign-in page offers every tenant's users. The user signs in to their own tenant, and iss and tid name it.
  • An application with signInAudience AzureADMultipleOrgs or AzureADandPersonalMicrosoftAccount gets a service principal in the user's tenant on consent.
  • A single-tenant application used through an alias gives AADSTS50194. A user from another tenant on a tenant-specific path gives AADSTS50020.
  • A code or refresh token redeemed on another tenant's path gives AADSTS700005.
  • The /__sim__ endpoints act on the primary tenant, except reset, which resets every tenant.

Conditional access

Policies are managed through Graph at /identity/conditionalAccess/policies, with Microsoft's conditionalAccessPolicy shape, so azuread_conditional_access_policy works. They are evaluated whenever a user token is issued: on the sign-in page, the device code page, and the password, refresh and on-behalf-of grants.

stateEffect
enabledEnforced
enabledForReportingButNotEnforcedEvaluated and logged, never enforced
disabledIgnored

A policy applies when all its conditions match:

  • Users: includeUsers (including All and GuestsOrExternalUsers), includeGroups (transitive membership), includeRoles (role template IDs, including active PIM assignments), includeGuestsOrExternalUsers, and the matching exclusions.
  • Applications: includeApplications and excludeApplications, matched against the client and the API. A policy for user actions or authentication contexts never applies to a sign-in.
  • Client app types: browser for the sign-in page, mobileAppsAndDesktopClients for the device code, password and on-behalf-of grants, and all.
  • Locations, platforms, devices, risk, authentication flows: the simulator has no such data. A policy that restricts one of them never applies; one that covers everything (All locations, all platforms, no risk levels) does.
  • A policy without a users condition (a workload identity policy) never applies.
Grant controlResult
blockRefused with AADSTS53003
mfa, or an authenticationStrengthThe sign-in page and the device code page add an "Approve sign-in" step. Tokens that carry amr then include mfa in it (see amr). Grants without a page answer interaction_required with AADSTS50076.
compliantDeviceCannot be met: AADSTS53000
domainJoinedDeviceCannot be met: AADSTS53001
Any other control, terms of use, custom controlsCannot be met: AADSTS53003

With operator OR, MFA satisfies the policy when it is among the controls. With AND, every control must be met.
