Microsoft Graph

General behaviour

  • Every request needs a bearer token the simulator issued for Graph (see token kinds). The tenant comes from its tid.
  • /beta serves the same handlers as /v1.0, because the Terraform azuread provider uses /beta for several resources.
  • Collections are ordered by object ID, so $skiptoken paging is stable.
  • Properties the simulator does not model are stored and returned unchanged, and an explicit null reads back as null. Terraform therefore sees no drift.
  • Write-only values never come back: owners@odata.bind and members@odata.bind are applied, not stored; secretText appears only in the addPassword response; a user's password never appears.
  • The identity that creates an application or a service principal becomes its initial owner when no owners are bound, as in Entra.
  • Writes are readable immediately.

JSON batching

POST /v1.0/$batch and POST /beta/$batch take requests, each with an id, a method, a relative url, and optional headers, body and dependsOn.

  • At most 20 requests; more, a duplicate id, or a malformed batch gives 400.
  • The batch itself needs a valid token. Each request runs through the same router with that token, so routing, permission checks and OData behave as in a direct call.
  • The answer is 200 with responses, each with id, status, headers and body.
  • A request whose dependency failed gets 424.

Delta queries

GET …/delta on users, groups, applications, service principals, directory roles and delegated permission grants.

  • The first call returns every current object and an @odata.deltaLink with a $deltatoken. Calling that link returns what changed since, and a new link.
  • $deltatoken=latest returns only a delta link.
  • Deleted objects come back as their id with @removed: {"reason": "deleted"}.
  • Group membership changes come back in members@delta.
  • $select limits what is tracked: a change to an unselected property does not return the object.
  • $filter supports only id eq '…', at most 50 IDs. $expand, $top and $orderby are refused for users and groups.
  • Prefer: return=minimal returns only changed properties.
  • Every round fits in one page; there is no @odata.nextLink.

Permission enforcement

Each Graph request is checked against the permissions Microsoft documents for that endpoint, generated from Microsoft's documentation into src/auth/permission_requirements.json.

  • A requirement is a list of alternatives, each a set of permissions held together. For example, POST /servicePrincipals/{id}/appRoleAssignedTo accepts AppRoleAssignment.ReadWrite.All with Application.Read.All, or AppRoleAssignment.ReadWrite.All with Directory.Read.All, or Application.ReadWrite.All alone. Half of an alternative is not enough.
  • An app-only token is judged on roles, a user token on scp. The two are never mixed.
  • A ReadWrite permission satisfies a requirement for the matching Read permission, as in Entra.
  • A refusal is 403 Authorization_RequestDenied, "Insufficient privileges to complete the operation."
  • A route the table does not cover is allowed, with a warning in the log.
  • --enforce-permissions false turns the check off.

Privileged Identity Management

Directory roles can be made eligible and activated through schedule requests, so azuread_directory_role_eligibility_schedule_request works.

  • A request needs action, principalId and roleDefinitionId (a role template ID); directoryScopeId defaults to /. An unknown principal gives 404 SubjectNotFound, an unknown role 404 RoleNotFound.
  • Every request completes at once with status Provisioned, with no approval step. The schedule it creates has the request's ID.
  • Actions: adminAssign, adminUpdate, adminExtend, adminRenew, selfActivate, selfExtend, selfRenew, adminRemove, selfDeactivate.
  • A self… request must be made with the principal's own token (403 otherwise). selfActivate needs a current eligibility for that role and scope (400 RoleAssignmentDoesNotExist otherwise).
  • scheduleInfo.expiration accepts noExpiration, afterDateTime and afterDuration (ISO 8601, such as PT8H). An activation without an end lasts eight hours; other schedules without an end do not expire.
  • An active tenant-wide assignment counts in wids, group claims, conditional access, assignment-required checks and the role's members until it ends. One scoped to /administrativeUnits/{id} counts only over that unit.
  • cancel is always refused, because no request is ever left pending.

Administrative units

Units support azuread_administrative_unit, azuread_administrative_unit_member and azuread_administrative_unit_role_member.

  • Members are users and groups, added with $ref.
  • A scoped role membership has roleId, the object ID of an activated directory role, and roleMemberInfo.id. Only the 14 roles Microsoft lists as assignable over a unit are accepted: Authentication Administrator, Attribute Assignment Administrator, Attribute Assignment Reader, Cloud Device Administrator, Groups Administrator, Helpdesk Administrator, License Administrator, Password Administrator, Printer Administrator, Privileged Authentication Administrator, SharePoint Administrator, Teams Administrator, Teams Devices Administrator and User Administrator.
  • With a user token, PATCH or DELETE on another user needs the signed-in user to be a Global Administrator or User Administrator tenant-wide, or a User Administrator over a unit the target is a direct member of, through a scoped role membership or a PIM schedule. Otherwise 403 Authorization_RequestDenied. Membership through a group in the unit does not count. Users may always update their own profile.
