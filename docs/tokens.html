Tokens

Every token is an RS256-signed JWT with a kid from the JWKS. Its claims come from the directory at the moment it is issued.

Three kinds of access token

Which kind is issued depends on the API the scope names:

APIFormatissaud
Microsoft GraphA fixed v2.0 claim sethttps://{public-host}/{tenant}/v2.0The simulator's base URL, https://{public-host}
A registered API with api.requestedAccessTokenVersion unset or 1v1.0https://sts.windows.net/{tenant}/The identifier URI or appId the client asked with; the appId when the aud optional claim has use_guid

The Graph aud is the simulator's URL, not https://graph.microsoft.com, because the simulator's Graph endpoints check that aud. A token for any other API is refused by Graph with 401.

An API validating v1.0 tokens reads the v1.0 discovery document at /{tenant}/.well-known/openid-configuration, whose issuer is the v1.0 issuer. v1.0 access tokens also carry an x5t header equal to kid.

ID tokens

ID tokens are always v2.0. aud is the client ID, and they carry iss, iat, nbf, exp, oid, sub, tid, ver, name, preferred_username and nonce when the authorize request had one. They also carry the user's roles on the client application, and the group and optional claims the client's registration asks for.

roles and scp

  • App-only token: roles holds the values of the app roles assigned to the client's service principal on the API.
  • User token: roles holds the app roles assigned to the user on the API, directly or through a security group the user is a direct member of. scp holds the scopes the user consented to for this client on this API.
  • A role or scope value is read from the API's definitions at issuance. Deleting an assignment, a grant or a role changes the next token.
  • Graph judges an app-only token on roles and a user token on scp only, so a role in a user token grants no Graph permission.

Group claims and wids

The groupMembershipClaims of the registration the token is for (the API for an access token, the client for an ID token) decides the group claims:

Settinggroupswids
null or Noneabsentabsent
SecurityGroupSecurity groups (transitive) and directory roles, as object IDsabsent
AllEvery group (transitive) and directory rolesThe user's directory role template IDs
DirectoryRoleabsentThe user's directory role template IDs
ApplicationGroupGroups assigned to the application that the user is a direct member ofabsent

The comparison ignores case. Directory roles include tenant-wide PIM assignments that are currently active.

The groups optional claim refines the format through additionalProperties: sam_account_name, dns_domain_and_sam_account_name and netbios_domain_and_sam_account_name use the group's on-premises attributes and leave out groups that lack them. cloud_displayname emits the display name, with ApplicationGroup only. emit_as_roles puts the group values in roles instead, replacing the app roles.

Above 200 groups, groups is replaced by the overage claims _claim_names and _claim_sources, pointing at https://graph.windows.net/{tenant}/users/{user}/getMemberObjects, as Entra does.

Optional claims

The optionalClaims.accessToken of the API, or optionalClaims.idToken of the client, adds:

ClaimRule
emailThe user's mail, when requested, or for a guest user, or in an ID token when the sign-in asked for the email scope
given_name, family_name, upnv2.0 tokens, when the sign-in asked for the profile scope
preferred_usernamev1.0 tokens
acct0 for a member, 1 for a guest

idtypAccess tokens, with include_user_token: user
audv1.0 access tokens, with use_guid: aud becomes the appId

A claim without a value is left out. Other optional claims are accepted on the registration and ignored.

amr

amr is ["pwd"], or ["pwd", "mfa"] after the MFA step that a conditional access policy requires. It appears in v1.0 user access tokens, and in v2.0 access tokens and ID tokens whose registration requests the amr optional claim. Graph tokens never carry it.

The signing key is generated at startup, so kid changes on every restart unless --signing-key gives a PKCS#8 PEM key. Codes, refresh tokens and sessions are held in memory and lost on restart or reset.
